# クライアントIPの設定（パッチ案）

## 設定場所と例

このパッチはサーバー単位のPHP定数 `DF_LIKE_TRUSTED_PROXIES` を新設します。既存の管理画面Config項目、環境変数、Composer設定ではありません。`POST/DFLikeToggle.php` が定数を読み、`Services/LikeClientIp.php` を既存の `Bootstrap.php` オートローダーで読み込みます。DB設定やラッパー生成先の変更は不要です。

a-blog cmsの起動時に読み込まれる `config.user.php` に、実際に管理下にあるプロキシだけを指定します。これは設置例です。このリポジトリにCMS本体の設定ファイルは含まれません。

```php
// CMSルートの config.user.php 内。IPは設置環境の値へ置換する。
define('DF_LIKE_TRUSTED_PROXIES', [
    '10.0.0.10',             // IPv4の単一プロキシ
    '2001:db8:100::10',      // IPv6の単一プロキシ（例示用アドレス）
    // '10.0.1.0/28',        // この範囲の全ホストが信頼済みプロキシの場合だけ
    // '2001:db8:200::/120', // IPv6 CIDRも指定可能
]);
```

未定義または空配列 `[]` なら転送ヘッダーを無視します。文字列・不正要素を含む配列も、一覧全体を無効として `REMOTE_ADDR` へ戻します。ドメイン名、ワイルドカード、`private_ranges` のような記法は対応しません。プライベートIPやループバックを自動で信頼することはありません。`0.0.0.0/0`、`::/0`、端末も入る社内LAN全体などを設定すると信頼境界を失うため、設定しないでください。

## 判定規則

1. `REMOTE_ADDR` が正しいIPv4/IPv6でなければ空文字を返し、転送ヘッダーを使いません。
2. 接続元が一覧に該当する場合だけ `X-Forwarded-For` を使います。
3. ヘッダー全要素が正しいIPであることを確認し、接続元から右→左へ信頼済みホップをたどります。最初の未信頼IPで止まり、それより左の自己申告値を使いません。全ホップが信頼済みなら左端を返します。
4. 要素には前後のスペース・タブだけを許可します。空要素、`unknown`、ポート付きIP、角括弧、IPv6ゾーンID、制御文字、不正IP、8192バイト超、64要素超はヘッダー全体を無視し、接続元へ戻します。
5. IPv6表記は正規化してからハッシュ化します。IPv4-mapped IPv6はIPv6のまま扱い、IPv4の信頼設定には一致させません。実環境でこの形式になる場合は該当するIPv6 IP/CIDRを明示します。

例: 接続元 `10.0.0.10`、XFF `203.0.113.99, 198.51.100.8, 10.0.1.2`、信頼済み `10.0.0.10` と `10.0.1.2` なら結果は `198.51.100.8` です。左端の追加値は使いません。中間プロキシが未登録ならそこで止まるため、本来の訪問者までたどるには経路中の各プロキシを登録します。

## 導入環境で確認すること

- PHPへ渡る `REMOTE_ADDR` が実接続元か、Webサーバーが復元した訪問者IPかを確認する。
- アプリ側で解決する場合: 信頼済みプロキシが観測した接続元IPをXFFへ必ず追加するか、入口で外部入力を上書きすること。利用者からのヘッダーをそのまま転送する設定では安全に復元できません。CDN/LB/内部プロキシを含む全段と、オリジンへの直接到達経路を確認する。
- nginxの `set_real_ip_from` / `real_ip_header` / `real_ip_recursive`、Apacheの `RemoteIPHeader` / `RemoteIPTrustedProxy` / `RemoteIPInternalProxy` が既に安全に訪問者IPを復元している場合: アプリ定数は未定義/空配列にし、復元済みの `REMOTE_ADDR` を使用する。二重解釈は避け、FastCGI等がPHPへ渡す値も確認する。
- `Forwarded`、`X-Real-IP`、`CF-Connecting-IP`、PROXY protocolをこのクラスは直接読みません。採用する場合は信頼済み経路でWebサーバーが検証・復元する設計を確認する。
- IPv4/IPv6双方、複数段、重複ヘッダーの結合、無効ヘッダー、プロキシ増減時のIP一覧更新をステージングで確認する。生IPの診断ログは必要最小限の管理下で扱う。

## 互換性と制限

設定前は全プロキシ利用者が接続元プロキシのIPとUser-Agentごとの枠を共有します。不正ヘッダー時のフォールバックも同様です。導入前にプロキシ設定を準備してください。直接接続ではXFFを付けてもIPを変えられなくなります。

Cookie、対象ごとの現在状態、DB構造、POST名、通知処理は変更しません。IPの取り方やIPv6表記が変わる利用者では既存履歴のハッシュと新しいハッシュが一致せず、移行後の最大10分程度は制限枠が継続しないことがあります。過去の生IPは保存されていないため再計算しません。

現在の制限はIP＋User-Agentごとの成功したlike履歴10回/10分です。User-Agent変更は別枠になります。Cookie変更だけではこの枠はリセットされませんが、対象＋訪問者Cookieによる一意性と3秒クールダウンは別訪問者になります。解除は10分制限の対象外（3秒クールダウンは適用）、再likeは再び加算されます。件数確認と保存は原子的ではなく、並行処理で10回を超える可能性が残ります。IP取得だけでこれらの仕様・課題は解消しません。

リポジトリにPHPの最低バージョンの明示やComposer定義はありません。既存コードにはnullable型/`void`等があります。このパッチも既存の静的サービス・配列・型宣言の様式に合わせ、PHP 8専用構文や追加ライブラリを使用しません。検証環境のバージョンと結果は提出レポートに記載します。

## DB不要のテスト

```bash
PHP_BIN=/path/to/php tests/run-client-ip-tests.sh
```

通常接続、偽装、単段/多段、IPv4/IPv6、全CIDRプレフィックス境界、不正入力、実際のPOSTラッパー/設定の受渡しを検証します。既存 `LikeRepository` の制限・Cookie・解除/再like・割込み順序のテストはメモリ内DB代替を使います。実SQL・ロック・本物の同時HTTPリクエスト・CMS表示・通知の統合試験ではありません。
